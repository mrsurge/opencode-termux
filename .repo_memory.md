## Repo-Wide Rule: No Fallbacks Unless Requested

- Rule: NO FALLBACKS PERIOD unless the user explicitly requests the fallback for the specific task.
- Rule: This is repo-wide and applies outside any provider, model, adapter, schema, UI, or validation context.
- Rule: Do not add synthetic defaults, hard-coded alternatives, compatibility shims, inferred capability mappings, silent substitute behavior, or "best effort" behavior that changes the semantic truth of the runtime/API.
- Rule: If the real source does not provide a value, capability, provider, model, variant, event, or field, expose that absence directly and make the missing behavior explicit.
- Why it matters: Fallbacks can make broken or unsupported behavior appear to work, which corrupts validation and misleads future implementation decisions.
